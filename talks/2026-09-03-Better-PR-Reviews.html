Code is documentation

...except it’s not.

It documents the code that’s running. That’s it.

It does not document:

What the committer intended to do.

Why that option was chosen.

What problem it was trying to solve.

Before requesting review

It must be: Focused. Understandable.
Revertible.

You have to understand it, not just the tool that wrote it.

Good / Bad

PR Titles

Good

Relevant title. Remember, we look at lists of these.

Bad

Title from the first commit. It may not be relevant when the PR is ready for review or merge.

Good / Bad

PR Descriptions

Good

Concise description with the problem we’re trying to solve and relevant context.

Bad

Fluffy description filling available space, wasting the reviewer’s time.

Good / Bad

Tests

Good

Have some. Ran some. Did a relevant deploy for most things. For example: Stamp for most things, ASE for deployment testing.

Bad

No tests. No deploy. Bad developer.

Tip 1

AI helped write it?

Tip 1

AI didn’t help write it?

Same thing. Use AI to do a first pass reviewing it.

Use the checks at your disposal to find any issue we can, as early as we can.

Tip 2

Pull unrelated fixes out ahead.

We use merge commits. Land the fix separately first.

Merge the fix
→
Update your branch
→
Diff disappears

Tip 3 · What I tell my kids

If you have to force a change
or it feels wrong, step back.

And don’t hesitate to ask for help.

Tip 4

Git worktrees are your friend.

Good for:

Multiple changes at once.

Keeping release branches around, including for local AI comparisons.

Reviewing other folks’ PRs locally when you need better tooling.
